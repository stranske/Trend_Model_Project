1. Standardize Monte Carlo costs: schema + update docs/examples

## Why

Monte Carlo cost configuration currently supports multiple shapes (`regimes:` mapping vs epic-style `kind: regime_stochastic` with `trade_cost_bps`). Without a canonical schema and updated documentation, scenario authors will keep guessing and configs will drift.

## Scope

Define and document the canonical `costs:` schema for Monte Carlo scenarios. Ensure all examples in `docs/phase-3/MonteCarlo.md` match the canonical format and that legacy formats are explicitly documented as supported (or deprecated).

## Non-Goals

- Changing the economics of the cost process (sampling math) beyond schema parsing/validation
- Adding new cost distribution families beyond fixed/normal/lognormal

## Tasks

- [ ] Decide canonical `costs:` schema (recommend: epic-style `kind: regime_stochastic` + `trade_cost_bps` + top-level regimes)
- [ ] Update `docs/phase-3/MonteCarlo.md` to use canonical schema in all examples
- [ ] Add a short “Backward compatibility” section documenting which legacy keys/aliases are accepted (`regimes:`, `dist`, numeric shorthand)
- [ ] Add/adjust at least one scenario YAML example using the canonical schema

## Acceptance Criteria

- [ ] Documentation examples for `costs:` match the canonical schema end-to-end
- [ ] At least one scenario in `config/scenarios/monte_carlo/` uses the canonical schema and loads successfully
- [ ] Legacy schema support is explicitly documented (supported vs deprecated)

## Implementation Notes

Files to modify:
- `docs/phase-3/MonteCarlo.md`
- `config/scenarios/monte_carlo/*.yml`
- (Optional) `src/trend_analysis/monte_carlo/costs.py` docstrings for schema notes

3. Document mixture-mode path generation + seeding contract

## Why

Mixture-mode has two legitimate execution modes:
- shared-path bulk generation (when per-path seeds match the base SeedManager)
- per-path generation (when seeds diverge)
Without a documented contract, users can misinterpret determinism and performance characteristics.

## Scope

Write down the deterministic rules for mixture-mode path generation and add a brief note about performance tradeoffs.

## Non-Goals

- Implementing new caching layers for per-path generation
- Adding runtime flags unless necessary for correctness

## Tasks

- [ ] Add a “Mixture mode seeding” section to `docs/phase-3/MonteCarlo.md`
- [ ] Document the exact condition under which bulk vs per-path generation occurs
- [ ] Add a short troubleshooting note (“why is my mixture run slower?”)
- [ ] (Optional) Add a debug log line when mixture chooses per-path mode

## Acceptance Criteria

- [ ] Documentation explains mixture mode determinism and performance at a glance
- [ ] Users can predict whether a run will use shared-path or per-path generation from config

## Implementation Notes

Files to modify:

- (Optional) `src/trend_analysis/monte_carlo/runner.py` for debug logging


4. Decide whether CASH injection should be gated (rf_override_enabled vs always)

## Why

Current CASH injection behavior can be interpreted two ways:
1) Always inject CASH when the risk_free_column is missing (simple, deterministic)
2) Only inject when rf override is explicitly enabled (more conservative)
We should make the intended policy explicit.

## Scope

Decide the gating policy and implement consistent behavior + tests.

## Non-Goals

- Changing how risk_free fallback selection works outside Monte Carlo
- Introducing new risk-free data sources

## Tasks

- [ ] Decide gating behavior for CASH injection:
  - [ ] Always inject (default), or
  - [ ] Only inject when `metrics.rf_override_enabled` is true
- [ ] Update `_apply_cash_handling` accordingly
- [ ] Update/add tests for both gating modes
- [ ] Document the decision in Monte Carlo docs

## Acceptance Criteria

- [ ] Behavior is consistent and covered by tests
- [ ] Documentation clearly states when CASH is injected and what rate is used

## Implementation Notes

Files to modify:
- `src/trend_analysis/monte_carlo/runner.py`
- `tests/monte_carlo/test_runner.py`
- `docs/phase-3/MonteCarlo.md`

5. Allow null for optional scenario sections in registry loader

## Why

Some scenario authors use `strategy_set: null` (or `outputs: null`, `costs: null`) to indicate intentional absence. Today this can error depending on strict mapping coercion.

## Scope

Allow `null` for optional sections (`strategy_set`, `outputs`, `costs`) in scenario parsing.

## Non-Goals

- Allowing `null` for required sections like `monte_carlo`
- Changing validation strictness for non-null mappings

## Tasks

- [ ] Update scenario parsing to treat `strategy_set: null`, `outputs: null`, `costs: null` as `None`
- [ ] Add a unit test scenario confirming null optional sections load cleanly

## Acceptance Criteria

- [ ] Scenario with null optional sections loads successfully
- [ ] Existing scenarios continue to validate as before

## Implementation Notes

Files to modify:
- `src/trend_analysis/monte_carlo/registry.py`
- `tests/monte_carlo/test_registry.py`
